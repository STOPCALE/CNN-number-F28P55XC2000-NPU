## Part 1 为什么需要卷积网络（从一个数组讲起）

### 1.1 问题的原始形态

一张 32×32 灰度图 = **1024 个数字**（0=黑背景，1=白笔迹）。
任务：把这段数组映射到 0~9 十个类别。最朴素的方案是**全连接（MLP）**。

### 1.2 全连接为什么不行（两个硬伤）

| 硬伤 | 具体表现 |
|---|---|
| **参数爆炸** | 第一层 1024→64 就要 `1024×64+64 = 65,600` 个参数；而本工程整个卷积套件第一层只有 **160** 个 |
| **没有平移不变性** | 数字往上挪 3px，对 MLP 来说是一整个"新样本"，它得把所有位置各学一遍 |

手写的本质：同一个"7"可以有无限种写法（位置、大小、倾斜、粗细都变）。
**我们需要一种对"局部模式在哪个位置出现"不敏感的模型结构。**

### 1.3 卷积的两个核心思想（这就是全部）

1. **局部连接**：一个 3×3 的"小模板"只看 9 个像素 → 学的是"边缘、角点、笔画"这类**局部模式**。
2. **权值共享**：同一套 3×3 模板**在整张图上滑动** → 无论"横杠"出现在左上还是右下，用的都是同一个模板。

产出物叫**特征图（feature map）**：模板滑过全图后得到的"哪里出现了这种模式"的强度分布。

> 一个卷积层有 16 个输出通道 = 学了 **16 个不同的模板**（16 种局部模式探测器）。

### 1.4 尺寸记账公式（以后所有 CNN 都这么算）

```
卷积输出边长 = floor((H + 2·pad − k) / stride) + 1
池化输出边长 = floor((H − k) / stride) + 1
```

本工程：卷积一律 `k=3, pad=1, stride=1` → **尺寸不变**；池化一律 `k=2, stride=2` → **减半**。
记住这两个约定，Part 2 的整条尺寸链你就能自己推。

### 1.5 感受野：每个输出点"看得到"原图多大

**感受野（Receptive Field）** = 输出图上一个像素，其数值受原图多大范围影响。
两层网络的感受野可以用递推算：

```
初始: RF = 1, 步长 J = 1
每过一层: RF = RF + (k − 1) × J ;   过完再: J = J × (stride)
```

迷你例子：`conv 3×3(s1)` 后 `pool 2×2(s2)`：
- conv：RF = 1 + (3−1)×1 = **3**，J 仍 1
- pool：RF = 3 + (2−1)×1 = **4**，J = 2

**为什么关心它**：感受野说明"深层特征是从多大上下文里长出来的"。
本工程的完整链（conv,pool ×3）→ 最后 4×4 特征图上每个点感受野 **22×22**（含 padding 的等效值），
≈ 覆盖整只手写数字——所以最后才能"拍板分类"。（自己推一遍 → 题库 B4）

### 1.6 为什么最后还是"全连接"

- 卷积+池化 = **特征提取器**（学"哪里有什么笔画"）
- 全连接 = **分类器**（把 512 个特征数字组合成"这是 3"的判决）

小 CNN 里两者分工明确：本工程 `Conv×3 + Pool×3 + FC×2`，就是经典的"特征提取 + 分类头"结构。

## Part 2 逐层拆解本工程网络（对照 `model.py` 看）

### 2.1 结构全景

```mermaid
flowchart LR
  i["输入 32×32×1"] --> c1["Conv 3×3 · 1→16"] --> p1["MaxPool 2×2"] --> c2["Conv 3×3 · 16→32"] --> p2["MaxPool 2×2"] --> c3["Conv 3×3 · 32→32"] --> p3["MaxPool 2×2"] --> f["Flatten → 512"] --> fc1["FC 512→64"] --> fc2["FC 64→10"]
```

尺寸链（自己用 1.4 的公式推一遍）：

```
32×32×1 →(conv,pad1)→ 16×32×32 →(pool)→ 16×16×16
        →(conv,pad1)→ 32×16×16 →(pool)→ 32×8×8
        →(conv,pad1)→ 32×8×8  →(pool)→ 32×4×4
        →(flatten)→ 512 →(fc)→ 64 →(fc)→ 10
```

### 2.2 输入层："口径"先行

- 单通道、32×32、取值 **[0,1]**、**白字黑底**（笔迹=1）。
- 这些不是随便定的：训练数据、手写板、将来固件里都是**同一口径**（见 Part 6）。
- 32 的来历：MNIST 原生 28×28，四周补 2px 黑边 → 32×32（**不是拉伸**，理由见 Part 3.2）。

### 2.3 Conv1（NPU 叫 FCONV）：16 个"笔画探测器"

- `3×3` 窗口 → 第一层只能看到"边缘/端点/小圆弧"这种最基础的图案。
- `pad=1` 的意义：让输出还是 32×32（尺寸不变），信息不丢边。
- 为什么 16 通道：想要多少种基础图案就开多少通道。16 是 4 的倍数——**这条是给 NPU 留的**
  （TI NPU 要求首层输出通道为 4 的倍数，见 Part 7 与 `docs/NPU合规设计说明.md`）。

### 2.4 ReLU：唯一的非线性

- `ReLU(x) = max(0, x)`：负数清零，正数原样。
- 为什么要它：卷积+池化全是**线性**操作，叠 10 层也等价于 1 层线性变换；插上 ReLU 才能把
  "模板A且非模板B"这类逻辑组合出来。
- 为什么不用 sigmoid/tanh：深层网络里它们会把梯度"压没"（梯度消失），ReLU 梯度要么 0 要么 1，好训。

### 2.5 MaxPool：减半、再减半、再减半

- `2×2` 窗口取最大值 → 边长减半。含义：**"这块 2×2 区域里，某模式最强烈的程度"**。
- 三个作用：
  1. 计算量：边长减半 → 下一层算量降到 1/4；
  2. 平移容忍：特征挪 1px 基本不影响池化输出；
  3. 抽象：越往后每个点携带的语义越"全局"。
- 为什么 max 不是 avg：max 保留"最强证据"，对 MNIST 这种"哪里有笔画很重要"的任务更合适。

### 2.6 Conv2 / Conv3：通道递增的直觉

- 16→32→32：每层输出是上一层模式的**组合**（弧+横杠→"弯钩"，等等）。
- 特征图越来越小（16→8→4）、通道越来越多（16→32）：**空间换语义**的经典节奏。

### 2.7 分类头：Flatten → FC 64 → FC 10

- `Flatten`：32×4×4 展平成 512 个数字（只是换个形状，无计算）。
- 两个 FC 之间夹 64 个隐藏单元：给"特征组合"留一层非线性空间。
- 最终输出 **10 个 logits**（未归一化得分）；概率 = softmax(logits)，推理时 **argmax 定类别**。
- 注意：模型里**没有 softmax 层**——这是故意留到应用端（手写板 Python 端 / 将来 C 端）做的。

### 2.8 参数账本（打开 `runs/cnn32/model.onnx` 或跑 `python model.py` 对账）

| 层 | 参数计算式 | 参数量 |
|---|---|---|
| Conv1 3×3, 1→16 | `1×16×3×3 + 16` | 160 |
| Conv2 3×3, 16→32 | `16×32×3×3 + 32` | 4,640 |
| Conv3 3×3, 32→32 | `32×32×3×3 + 32` | 9,248 |
| FC1 512→64 | `512×64 + 64` | 32,832 |
| FC2 64→10 | `64×10 + 10` | 650 |
| **合计** | | **47,530**（int8 权重 ≈ 46.4 KB） |

**读账心得**：小 CNN 里 FC1 占了 69% 的参数——因为 512 个输入全连到 64 个神经元。
这也解释了为什么"把最后特征图做小一点/通道少一点"能省参数：省的是 FC1。

### 2.9 算力账本（MACs = 乘加次数，衡量"跑一次要算多少"）

| 层 | MACs 计算式 | 次数 |
|---|---|---|
| Conv1 | `16×32×32 × (1×3×3)` | 147,456 |
| Conv2 | `32×16×16 × (16×3×3)` | 1,179,648 |
| Conv3 | `32×8×8 × (32×3×3)` | 589,824 |
| FC1 | `512×64` | 32,768 |
| FC2 | `64×10` | 640 |
| **合计** | | **≈ 1.95 M** |

**读账心得**：算力大头在 **Conv2**（60%）。第一层卷积反而便宜——因为它只有 1 个输入通道。
2M 次乘加对 MCU 世界的 NPU 是很轻的负载（参考：同平台历史 MLP 实测 637 µs/次，CNN 的绝对耗时留给板端实测）。

### 2.10 和 LeNet-5 的关系

LeNet-5（1998，手写数字的鼻祖网络）：`Conv3×3(1→6) → Pool → Conv3×3(6→16) → Pool → FC×3`。
本工程是它的现代强化版：通道翻倍到 16/32/32、多了一个卷积块、ReLU 替代 sigmoid、Adam 替代 SGD。
**你现在写的这个网络，就是"能上 NPU 的 LeNet"**。

## Part 3 数据管道：模型吃到嘴里的到底是什么

### 3.1 数据来源与格式（`dataset.py`）

- MNIST：60000 训练 + 10000 测试，28×28 灰度，官方标签 0-9。
- 我们**手写解析 IDX 格式**（`gzip` + `struct`，不依赖 torchvision）：
  魔数 `2051`=图像、`2049`=标签，大端序。这是理解"数据集到底是什么"的好机会。

### 3.2 为什么 pad 到 32 而不是拉伸到 32

- 拉伸：28→32 把笔迹放大 14%，**笔迹粗细分布变了**（训练分布≠其它场景的老数据分布）；
  还引入插值伪影。
- pad：只在四周补黑边，**数字本身一个像素都不动**。测试、手写板、未来固件都用同一种"数字装在中间"的构图。

### 3.3 为什么归一化到 [0,1]

- 数值稳定：输入在 [0,1]，配合小学习率，训练不发散。
- **量化对齐**：0~1 的浮点范围天然对应 int8 量化区间（Part 7 详解）——这是留给 NPU 的伏笔。

### 3.4 增广三件套（`dataset.py`，训练时按 batch 随机）

| 手段 | 实现 | 模拟了什么 |
|---|---|---|
| 旋转/平移/缩放 | `warp()`：`affine_grid` 生成"目标→源"采样网格，`grid_sample` 双线性采样 | 手写时角度、位置、大小千变万化 |
| 加粗 | `max_pool2d`（≈形态学膨胀） | 笔尖粗 |
| 变细 | `-max_pool2d(-x)`（≈腐蚀） | 笔尖细 |

**两个工程要点**：
1. 增广在 **GPU 上按 batch** 做（几毫秒），不是预生成数据集——每轮都是"新样本"，等效数据无限。
2. `warp()` 也被 `evaluate.py` 的鲁棒性测试复用——**同一套变换代码**，测试口径与训练口径天然一致。

### 3.5 为什么要留出测试集

测试集（10000 张）**从不参与训练**。它是"高考"，专门测"没见过的新样本"。
如果拿它调参又拿它报分，分数会虚高——这叫数据泄漏。本工程的做法：训练只碰 60000 张训练集。

## Part 4 训练到底在做什么（`train.py` 逐句拆）

### 4.1 一轮（iteration）的四步

```
① 取一批图 xb（128 张）+ 标签 yb
② 前向: logits = model(xb)          # 32×32 → 10 个得分
③ 损失: loss = cross_entropy(logits, yb)   # "错得有多离谱"一个数
④ 反向: loss.backward() → 每个参数得到一个梯度 → Adam 按梯度更新参数
```

跑 60000/128 ≈ 469 步 = 1 个 epoch；15 个 epoch 收敛。

### 4.2 cross_entropy 在做什么（简版）

`logits → softmax 变概率 → 取"正确类"的概率 → 取负对数`。
正确类概率越接近 1，损失越接近 0。它比"分类错误率"平滑得多——**有梯度，才能被优化**。

### 4.3 Adam 与余弦退火（直觉即可）

- Adam：给每个参数单独调"步长"，前期快、后期稳。学习率 `lr=1e-3`。
- 余弦退火（`CosineAnnealingLR`）：lr 从 1e-3 平滑降到 0——最后几轮"小步微调"，帮 loss 落进更平的谷底。

### 4.4 解读训练曲线（runs/cnn32/history.json）

```
E01 test 0.9660 → E05 0.9822 → E10 0.9909 → E14 0.9923 → E15 0.9920
```

- **看趋势不看单点**：E04→E05 有回跌（0.9833→0.9822），噪声而已，别慌。
- **怪现象：train acc（0.9789）< test acc（0.9920）？**
  不是 bug——train 的 97.9% 是在**加了旋转/平移/变粗的困难样本**上打的分；
  test 是干净 MNIST。增广让训练"更难"，模型被迫学"本质形状"而不是"死记位置"。
  **这正是增广在起作用。**（做实验 E2 你可以亲手验证）

### 4.5 为什么保存的是 epoch 14 而不是最后一轮

`train.py` 每轮测一次，谁分高留谁（`best.pt`）。第 15 轮 0.9920 略低于第 14 轮 0.9923，
属于正常波动——**选"最好的一次"比"最后一次"稳**。
（严谨注：这里用测试集做了选模参考，MNIST 惯例如此；正式项目应另切验证集。）

### 4.6 为什么这个网络 2 分钟就能训完

- 47k 参数 / 1.95M MACs：模型极小；
- 增广在 GPU 上按批做；
- 数据集能整块放进内存。
**"训练迭代快"本身就是模型设计的一部分**——小网络让你一天能跑 50 个对照实验。

## Part 5 评估：别只信一个数字（`evaluate.py`）

### 5.1 混淆矩阵（`runs/cnn32/confusion.png`）

测试集 99.23%。每类准确率：

```
0:99.69  1:99.56  2:99.52  3:99.21  4:99.29
5:99.33  6:99.06  7:99.22  8:98.77  9:98.61   ← 最差两类
```

**怎么看**：找对角线以外的数字 = "谁被认成谁"。打开 `errors.png` 看 25 张错例，
自己判断"这几张是不是连人都会犹豫"——这是训练"模型直觉"的最好练习（实验 E5）。

### 5.2 鲁棒性曲线：位置、角度各有多少容差

| 扰动 | 准确率 |
|---|---|
| 平移 +1px | 99.10% |
| 平移 +2px | 98.10% |
| 平移 +3px | 92.39% |
| 平移 +4px | **70.44%** |
| 旋转 ±10° | 98.8 ~ 99.1% |
| 旋转 ±20° | 96.3 ~ 96.5% |

**读法**：训练增广只覆盖 ±2px，所以 ±2px 内几乎无损；±4px 进入"训练没见过"的区域，直接崩。
**结论**：模型对位置的"免费容差"很小 → 这就是为什么预处理必须**质心居中**（Part 6）——
把用户画的任意位置，归一化回"训练时的标准位置"。

### 5.3 字体渲染代理测试（99.33%）

用系统 5 种字体渲染 0-9（150 张），走**与手写板完全相同**的预处理再预测。
它说明：**只要预处理口径对，模型对"非 MNIST 笔迹"的泛化是好的**。
它不能替代手写板——但它是上场前最便宜的"压力测试"。

### 5.4 权重 int8 模拟（99.21%）

把权重粗暴地压成 8bit 网格再复原，精度几乎不掉（99.23→99.21）。
说明**这个网络天生抗量化**（小核、ReLU、无 BN），和 Part 7 的真量化结果互相印证。

### 5.5 手写板自检（`draw_ui.py --selftest`）

合成笔迹 → 预处理 → 推理：直线→1（100%）、圆→0（100%）、S 形→5（100%）。
它验证的是**整条管线**，不是单层。三层防线记牢：

```
单测(selftest) → 分布(confusion/errors) → 压力(shift/rot) → 代理(font) → 端到端(UI 手写)
```

## Part 6 预处理：全工程最不起眼、也最要命的地方（`preproc.py`）

### 6.1 唯一原则：训练分布 = 部署分布

模型只认识"**MNIST 风格**的输入"：数字~20px 大小、**质心居中**、白字黑底、[0,1]。
手写板、评估脚本、未来固件——任何产生输入的地方，**都必须走同一条流水线**。
历史上无数"测试 99%、上手就崩"的事故，90% 是这里断的（这条也是你其他工程的铁律）。

### 6.2 四步流水线，每一步为什么

```
① 包围盒裁剪      —— 裁掉空白, 把注意力对准数字
② 长边缩到 20px   —— 复制 MNIST 官方"20 内容盒"的尺度约定（数字大小先统一）
③ 质心平移到 (14,14) —— MNIST 官方的对齐方式; 让"笔画密度中心"回到画布中心
④ 四周补 2px → 32×32, /255 —— 与训练数据完全同构
```

- 为什么是**质心**不是外框中心：像"1/7"这种一边重的字形，质心对齐才能保证"笔画密度分布"与训练一致。
- 为什么第 ② 步正好 20：训练数据就是这么造的（MNIST 官方做法），多一像素都算分布漂移。

### 6.3 易错点：白底黑笔要翻转

画板显示是"白底黑笔"（人类习惯），模型口径是"白字黑底"。

## Part 7 从 PC 到 NPU：量化与部署视角的 CNN

### 7.1 NPU 是"挑剔的加速器"

TI F28P55x 里有一个神经网络加速器（NPU）。它只知道几种"规定动作"（FCONV/GCONV/PWCONV/FC/池化……），
**不满足它规矩的层会被静默退回 CPU 执行**——不报错，只是没加速。
所以正确姿势：**从设计网络的第一天就按它的规矩来**（本工程就是这样，依据 `docs/NPU合规设计说明.md`）。

### 7.2 本网络"体检表"（对照官方 NPU 配置指南）

| 约束 | 本模型 | 状态 |
|---|---|---|
| 首层卷积 iC=1、oC 为 4 的倍数 | Conv 1→16 | ✅ |
| 中间层通道数为 4 的倍数 | 16 / 32 / 32 | ✅ |
| MaxPool 至少一维 ≤4 | 2×2 | ✅ |
| FC 输入特征 ≥16 | 512 / 64 | ✅ |
| batch=1、静态形状 | (1,1,32,32) | ✅ |
| 图里禁用 MatMul+独立 Add（FC 要 Gemm 形态） | 导出后是 Gemm | ✅ |

### 7.3 QAT 速览：怎么把浮点模型"压"进 int8

- **假量化**：前向时把权重/激活按刻度四舍五入到 int8 网格，再假装还原继续算——网络"体会"到量化误差。
- **STE（直通估计）**：四舍五入不可导，反向时耍赖——梯度直接穿过（当作恒等函数）。
- **observer**：统计每层数值范围，决定"刻度"多粗。日志里 `Freezing ranges` 之后再训练，
  刻度冻结、速度大增（后期 epoch 从几百秒降到几十秒；本机 CPU 负载也有波动，变化并非严格单调）。
- **为什么是自蒸馏**：本工具链的损失函数只有 mse/l1/huber（没有交叉熵）。于是"教师"= 复制一份 float 模型，
  "学生"= 量化模型，让学生临摹老师的输出（`loss=mse(学生(x), 教师(x))`）。
  项目里的 `adapter_mnist_cnn.py` 就是干这个的。

### 7.4 编译结果怎么读（卸载表 + 内存账）

```
上 NPU [X]: FCONV×1, GCONV×2, FC×2, MAXPOOL×3, PAD×2      ← 所有"算得多的层"
回落 CPU [ ]: add/mul/floor/clip/cast/reshape/flatten/…        ← 量化胶水 + 数据搬运
```

**读法**：判断重要性看两点——① 是不是计算大头（MACs 口径）；② 是不是 O(元素数) 的搬运/转换。
两类 CPU 算子都是后者，量级可忽略。**0 警告 + type=hard** = 真 NPU 全速模式。

mod.a 内存账（就是上板要放进 Flash/RAM 的东西）：

```
Code 1.76 KB (程序) + RO 41.88 KB (权重) + RW 24.98 KB (激活/工作区) = 68.63 KB
```

### 7.5 int8 的代价

200 样本验收：float 99.5% → int8 99.0%（n=200 时 1 个样本=0.5%，差 1 个样本；结论是**量化损失很小**）。
配合 5.4 的模拟（99.21%）可以放心：这个网络量化后被"伤"得很轻。

### 7.6 从 PC 到板子的全景

```
runs/cnn32/best.pt（你训的）
  → adapter（复用同一份 model.py 代码，单一事实源）
  → TI-QAT → mnist_cnn_int8.onnx（审计 0 警告）
  → ti_mcu_nnc 编译 → mod.a + tvmgen_default.h
  → CCS 集成（抄 E:\desk\CCS\npu_and_charge）→ 板端 while(!tvmgen_default_finished)
```

### 7.7 板端实测（2026-10-09，数字说话）

| | 完整版 (16,32,32) | 轻量版 (8,16,16) |
|---|---|---|
| 参数 / MACs | 47,530 / 1.95M | 20,666 / 0.53M |
| PC 测试集 float | 99.23% | 98.59% |
| 板端 golden 12 张 | 12/12 全对 | 12/12 全对 |
| 板端推理耗时 | **10.95 ms** | **4.91 ms** |
| mod.a 内存 | 68.63 KB | 36.12 KB |

- 耗时粗拟合：`T ≈ 2.6 ms + 4.3 ns × MACs` → 这块 NPU 是"小算力密度"型（边际 ≈ 1.5 MAC/周期@150MHz）；
  **加速的第一杠杆是减 MACs**（轻量版 MACs -73% → 时间 -55%），不是写更花哨的代码。
- 冷启动 = 稳态（10950.2 vs 10950.6 µs）：NPU 没有明显的"预热"效应。
- 板端 int8 输出 vs PC float 输出 max|d| = 0.591 → 与 PC 端量化验收（0.695）同量级：**量化噪声可控**。
- 闭环演示（2026-10-09 追加）：手写板"板端推理"按钮 = 手写输入 → 串口 → 板端 NPU → 回读结果+耗时
  （实测 10.91 ms 与板端自测一致；协议 `A5 5A`+1024B 像素 → 文本回包）——**这就是"硬件到应用"的最后一公里**。

## Part 8 实验手册：把"看懂"变成"证据"

纪律（沿用你另外两个工程的铁律）：**一次只改一个变量；结果写进新目录对照；看完复原。**

### E1 容量对照：把通道减半会怎样？

- **假设**：参数、算量大约降到 1/2~2/3，精度可能掉一点点。
- **改哪**：`config.py` 搜索 `conv_channels: Tuple[int, int, int] = (16, 32, 32)` → 改 `(8, 16, 16)`。
- **跑**：`conda run --no-capture-output -n torch python train.py --out-dir runs/e1_small`
- **看**：`runs/e1_small/report.json` 对比 `runs/cnn32/report.json`（参数量在 train.py 开头的层表里）。
- **附加**：再试 `(32, 64, 64)` → `--out-dir runs/e1_big`。三个尺寸画一条"容量-精度"曲线。

### E2 增广消融：没有增广会发生什么？

- **假设**：train acc 冲到 99.9%，但平移/旋转鲁棒性曲线明显变差。
- **改哪**：`train.py` 里注释掉这两行（Ctrl+F 搜索串）：
  - `random_affine_batch(xb`
  - `random_thick_batch(xb`
- **跑**：`... python train.py --out-dir runs/e2_noaug`，然后 `... python evaluate.py --ckpt runs/e2_noaug/best.pt --quick`
- **看**：两个 report/eval JSON 的 `shift`/`rot` 字段差异；再跑 `draw_ui.py` 亲手写几个字对比。
- **意义**：亲手体验"数字好看 ≠ 泛化好"。

### E3 破坏预处理口径：20px 盒改成 28px

- **假设**：字体代理测试分数明显下降（字体字形尺寸与训练分布不符）。
- **改哪**：`preproc.py` 搜索 `k = 20.0 / max(h, w)` → 改 `k = 28.0 / max(h, w)`。
- **跑**：`... python evaluate.py`（看 `[font-proxy]` 一行和 eval_report.json）。
- **复原**：改回 `20.0`。**意义**：体会"口径"两个字值多少分。

### E4 4bit 权重模拟：量化到底多疼？

- **改哪**：`evaluate.py` 搜索 `s = p.abs().max() / 127.0` → 改 `/ 7.0`（模拟 4bit）。
- **跑**：`... python evaluate.py --quick`，看 `[int8-sim]` 那一行前后变化。复原为 `127.0`。

## Part 9 易错点总清单（Top 10）

1. **白底黑笔不翻转** → 输入全反，手写板集体误判。自查：预览小图里笔迹应是亮的。
2. **预处理重写/不一致** → "测试 99%、手写 30%"的经典事故。只准用 `preproc.py`。
3. **别信终端里的长输出** → 结果都在 `runs/*.json`，以文件为准（本机老坑）。
4. `torch.load` 读含配置的 checkpoint 要 `weights_only=False`。
5. ONNX 是 batch=1 静态形状，onnxruntime 对拍要**逐张**喂。
6. **train acc < test acc 不是 bug**，是增广在干活（E2 可验证）。
7. 调参前先看**混淆矩阵+错例**——96% 和 99% 的问题可能完全不同。
8. NPU：不满足约束的层**静默回落 CPU**——只看"有没有报错"会错判，要看卸载表 `[X]/[ ]`。
9. 量化：通用 ORT-PTQ 上不了 TI NPU，必须走 TI-QAT（本工程工具已封装）。
10. **口径一致性 > 调参**（跨工程铁律，本工程把它做成了 `preproc.py` 唯一实现）。
